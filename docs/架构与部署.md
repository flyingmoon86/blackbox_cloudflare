# 架构与部署

更新日期：2026-09-11。前后端优化已联合发布，生产迁移到 0012；具体版本与验证结果见文末。

## 架构和目录

网站使用 TypeScript + Hono 单 Worker，D1 保存业务数据，R2 保存文件。匹配 public/ 中的公开静态资源由 Static Assets 直接响应；其他请求进入 Worker，执行身份和权限检查。

- src/routes/：URL、输入检查和页面响应。
- src/services/reviews.ts：审核事务入口；0009 的触发器在同一事务内创建档案或角色并写审核历史。
- src/services/uploads.ts、upload-policy.ts：上传状态、分片完成恢复、分类上限、容量预留。
- src/services/file-cleanup.ts、avatars.ts：删除重试和头像替换。
- src/services/resource-files.ts：文件类型、HEAD、Range 和条件请求。
- src/middleware/：登录状态、限流、安全头、缓存与错误编号。
- src/views/、src/views.ts、public/：页面、样式和浏览器交互。
- scripts/backend/：合成数据测试及真实 workerd/D1/R2 本地验收。
- scripts/data/：数据迁移、重复预检和快照升级验证。
- migrations/：只新增迁移，不修改已上线的 0001–0008。
- legacy-python/：原站功能对照，不进入 Worker 运行包。
- migration-work/：真实备份和迁移中间文件，禁止提交 Git。

## 本轮上传与存储规则

正式环境采用 Worker 绑定 R2，当前只需要 SESSION_SECRET；不需要 S3 访问密钥。原 local 数据库值继续表示绑定上传，保留旧任务兼容。S3 适配代码保留供以后验证，当前上线和容量验收不启用 S3 直传。

1. 队员或管理员创建任务；普通账号先认证。
2. 校验视频禁用、分类大小、作品、提交频率和容量。剧照 20MiB、剧本 50MiB、音频/其他 100MiB；页面沿用 MB 简写。头像仍为 15MiB。
3. 首次启用时分页核对现有 R2 对象，已有头像、资料、预览都计入预算；未核对完成时暂停新上传。
4. 原文件与预览先预留容量。已用加预留达到 9,000,000,000 字节附近时，不能创建超出预算的任务；每账号最多 3 个未释放上传预留。
5. 保留 50MiB 分片，浏览器逐片上传；FixedLengthStream 校验实际字节数，避免完整分片进入 Worker 内存。
6. 合并成功后，在一个 D1 batch 中入库、关联任务和转移容量台账。响应丢失或 D1 暂时失败时，后续请求复用已完成的 R2 对象。
7. 队员上传待审核；管理员上传延续直接入库规则。视频仍关闭。
8. 删除先移除数据库引用并记录清理任务，再删除 R2。失败保留任务及占用；定时任务每小时运行一次，分批重试。共享引用的对象暂不删除。
9. 没有七天回收站。R2 成功删除后不能依靠 D1 SQL 备份恢复文件内容。

“存储与服务状态”显示台账和清理任务，不能替代 Cloudflare 账单、操作数或账户总额度。9GB 仅约束网站新增上传；手工导入和其他应用写入不受网站控制。

FixedLengthStream 说明：[Cloudflare Streams](https://developers.cloudflare.com/workers/runtime-apis/streams/transformstream/)。

## 审核、认证和文件访问

- 审核只允许 pending 状态转换一次。新档案、账号绑定、演职员写入和处理历史保持原子性。
- 同角色多人演出和一人多角合法，只限制同作品、同队员、同类别、同角色的完全重复记录。
- 审核历史保留结果、理由、时间和处理人；删除处理人账号后显示“已删除的管理员”。历史缺失的处理人和时间不会伪造回填。
- 旧 scrypt 密码继续验证；改密码、禁用和解绑仍让旧会话失效。
- 登录、注册、改密码、申请、建议、上传任务和头像都有频率限制。限流键经 HMAC 处理，不保存明文 IP。
- 动态页面不缓存。受控文件每次重新检查身份和引用，允许通过 ETag 复用字节。
- 不信任文件原 MIME；HTML、SVG、JavaScript 等可执行格式作为附件下载。PDF、图片和常见音视频按支持的类型预览。
- /health 仅为存活检查；/admin/system/check 为管理员低频依赖检查。错误带请求编号，日志不输出密码、Cookie 或文件正文。

## 本地检查

使用 Node.js 24 或更新版本：

~~~powershell
npm ci
npm run db:init
npm run test:backend
npm run deploy:check
npm run dev
~~~

db:init 只升级本机 D1。有冲突时不要删除数据库。已有 .dev.vars 时保留原文件。点击步骤见 [本地验收指南](本地验收指南.md)。

## 下一次生产发布顺序（本轮未执行）

生产资源：域名 npublackbox.online，D1 blackbox-production，R2 blackbox-files-production。本轮增加 0009、0010、0011，必须先完成兼容迁移，再部署新代码。

1. 选择少人使用的窗口，先运行 npm run db:production:backup。SQL 导出只保护 D1，另外确认 R2 文件已有独立保留副本。
2. 执行只读预检：

~~~powershell
node scripts/wrangler.mjs d1 execute blackbox-production --env production --remote --file scripts/data/review-preflight.sql
~~~

两项 conflicts 必须为 0；非零交给管理员确认，不自动删行。唯一约束也会在有冲突时阻止迁移。

3. 用该次导出执行内存升级验证：

~~~powershell
node scripts/data/verify-backend-upgrade.mjs "实际的优化前SQL备份路径"
~~~

4. 运行 npm run deploy:check，包含格式、类型、旧数据转换、后端测试和不发布打包。
5. 运行 npm run db:production:migrate，再运行 npm run deploy。
6. 运行 npm run smoke:production，人工检查登录、上传、审核历史、存储状态、预览和下载。
7. 确认首次容量扫描完成，再邀请队员继续上传。观察请求量、CPU、D1 行读写、R2 字节和操作数。

备份不能覆盖回灌已有测试数据。新增迁移不删除旧表或列；回退代码时保留新结构，优先修复后重新发布。若回退到没有容量台账的旧上传实现，应先暂停上传，并在重新启用新版本前重新核对容量，避免漏计。
