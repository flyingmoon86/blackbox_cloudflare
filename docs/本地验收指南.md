# 本地验收指南（第一次运行）

这套步骤只在你的电脑上启动测试网站，不会发布到互联网，也不会连接正式数据库。

## 一、打开项目终端

在资源管理器打开：

```text
D:\大三\blackbox_cloudflare
```

在文件夹空白处右键，选择“在终端中打开”。确认终端提示符最后是 `blackbox_cloudflare>`。

## 二、第一次准备

依次复制并执行：

```powershell
npm install
Copy-Item .dev.vars.example .dev.vars
npm run db:init
```

如果提示 `.dev.vars` 已存在，可以跳过第二条。这个文件只保存本机测试密钥，不会上传 GitHub。

## 三、启动网站

执行：

```powershell
npm run dev
```

看到类似下面的文字即表示启动成功：

```text
Ready on http://127.0.0.1:8787
```

按住 `Ctrl` 点击该网址，或复制到浏览器打开。测试期间不要关闭这个终端。

## 四、按顺序检查

1. 未登录首页先显示“测试须知”；确认后看到“这里是黑匣子”、登录和注册入口。
2. 点击“注册”，创建一个测试账号。密码需要 8–128 位。
3. 用刚注册的账号登录，首页应显示“欢迎回来”。
4. 打开“个人中心”，确认用户名、身份和邮箱状态正确。
5. 先故意输入错误的当前密码，网站应拒绝修改。
6. 再输入正确的当前密码并设置新密码，网站应回到登录页。
7. 旧密码应无法登录，新密码应可以登录。
8. 在个人中心点击“退出登录”，应回到未登录首页。

测试账号只存在于本机 D1 模拟库，不会出现在 GitHub 或未来正式网站。

## 五、停止网站

回到运行网站的终端，按：

```text
Ctrl + C
```

## 六、只检查代码能否构建

不打开网站时，可执行：

```powershell
npm run typecheck
npm run build
```

两条命令都无报错，表示 TypeScript 类型检查和 Cloudflare 模拟打包通过。`npm run build` 不会发布网站。

## 七、代理地址错误

项目的 npm 命令会自动把误写成 Markdown 链接的代理变量还原为纯网址。如果升级依赖后再次看到 `TypeError: Invalid URL`，请先确认运行的是最新版代码，再执行 `npm run dev`。

## 八、验收管理员审核

1. 用普通测试账号提交一条队员认证申请。
2. 使用管理员账号进入“管理员工作台”，分别测试通过和驳回；驳回时必须填写理由。
3. 申请人重新登录后，应在个人中心看到结果。
4. 管理员可禁用其他测试账号，但不能禁用自己。

## 九、验收作品与演职员

1. 管理员打开“作品与资料”，点击“创建作品”。
2. 填写名称、年份、短介绍和剧情介绍并保存。
3. 在作品详情中从队员下拉列表选择人员，分别添加演员角色和后台分工。
4. 确认两类人员分组显示，并可点击姓名进入队员档案。
5. 编辑作品标题或介绍并保存。
6. 用普通账号登录，确认可以查看作品，但看不到编辑和删除操作。
7. 给该作品提交剧本、剧照或视频并由管理员审核通过，返回作品详情后，应在“相关资料”中看到资料并能打开详情。
8. 待审核或已驳回的资料不应出现在作品详情的“相关资料”中。
9. 用认证队员在作品详情选择“演员”或“后台与创作”，填写角色或分工并提交加入申请。
10. 管理员从工作台进入“作品加入审核”，通过后该队员和分工应出现在作品演职员名单；驳回时必须填写理由。
11. 管理员创建或编辑作品时，应能勾选未归类的待审核和已入库资料；待审核资料即使关联后也不能提前显示给普通用户。

## 十、验收公告与首页

1. 管理员进入“管理员工作台”，点击“管理公告”并发布一条测试公告。
2. 回到登录后首页，确认公告入口出现在首页内容中，顶部导航没有“公告”。
3. 退出登录后直接打开 `/announcements`，应先跳到登录页面。
4. 管理员进入“页面管理”，编辑首页欢迎语、剧团介绍和联系说明。
5. 从已有作品中指定一部“精选大戏”并保存。
6. 退出登录，确认剧团信息与联系我们左右并列，并显示精选大戏。
7. 未登录点击精选大戏，应先登录；登录后进入对应作品。
8. 管理员登录首页，点击文案旁的编辑入口，应跳到页面管理的相应位置。
9. 登录首页仍显示招新和关于我们，快捷入口包含首页、作品与资料、队员名录、个人中心。
10. 普通账号显示“这里是黑匣子”，认证队员和管理员显示“黑匣子永远是你的家”；管理员可分别编辑两类欢迎语。
11. 管理员修改测试须知后，在浏览器重新打开首页应再次弹出；不修改内容时，确认一次后不重复弹出。
12. 认证队员从关于我们进入意见箱提交建议，管理员从工作台进入建议收件箱并标记已处理。

## 十一、验收资料提交与审核

1. 用已认证队员账号进入“作品与资料”，点击“提交资料”。
2. 填写标题、类型、所属作品或“其他资料”、原文件名和说明并提交。
3. 打开“我的提交”，确认状态显示“等待审核”；此时该资料不应出现在公共资料库。
4. 用未认证普通账号直接打开 `/resources/submit`，应看到完整的认证说明页和申请认证按钮。
5. 管理员进入“管理员工作台”，点击“审核资料”。
6. 尝试不填理由直接驳回，网站应拒绝；填写理由后可正常驳回。
7. 队员在“我的提交”中应看到“已驳回”和管理员理由。
8. 再提交一条资料并由管理员通过，确认它出现在资料库并可进入详情页。
9. 详情页应提示文件已经保存但等待审核；审核通过后显示“下载文件”。
10. 类型选择“剧照”后，一次选择多张图片；完成后“我的提交”中每张剧照都应有独立的待审核记录。
11. 管理员可逐张通过或驳回；资料库按作品显示，每部作品只有一块剧照集卡片，内部排列该作品的全部已入库剧照。

## 十二、验收队员档案与帮助页

1. 用已认证队员账号打开“个人中心”，点击“维护我的队员档案”。
2. 修改个人简介和代表作并保存；姓名、年份和届别不应出现在队员自助表单中。
3. 返回自己的队员详情，确认新内容和“编辑我的简介与代表作”入口都存在。
4. 用管理员打开任一队员详情，点击“编辑队员档案”，确认管理员可修改姓名、年份、届别、简介和代表作。
5. 普通登录用户从个人中心进入“使用指南”，只能看到队员指南。
6. 管理员进入“使用指南”，应同时看到队员指南和管理员指南。
7. 管理员点击指南旁的编辑入口，应直接跳到“页面管理”的对应输入框。
8. 修改两份指南并保存，再分别用普通账号和管理员账号检查可见范围。

## 十三、验收 R2 文件与图片

拉取本次更新后先执行一次：

```powershell
npm run db:init
```

这会应用新的上传分片表。然后启动网站并按以下顺序检查：

1. 已认证队员打开“上传资料”，选择一个本地测试文件并开始上传。
2. 上传进度应增长，完成后进入资料详情，状态为“等待审核”。
3. 可用较大文件测试断点续传：上传一部分后关闭页面，重新进入并选择同一个文件，应提示继续上次任务并跳过完成的分片。
4. 上传过程中点击“取消上传”，页面应显示“上传已取消”。
5. 管理员审核通过后，详情页出现下载按钮；视频播放器或下载工具请求文件片段时支持 Range。
6. 管理员从工作台进入“管理资料”，可修改标题、类型、归属作品和说明，也可删除文件。
7. 队员在“维护我的档案”中上传 JPG、PNG、WebP 或 AVIF 头像；伪造格式和超过 15MB 的图片应被拒绝。
8. 管理员编辑作品时，只能从该作品审核通过的剧照中选择封面。
9. 管理员在“页面管理”中，从审核通过的剧照里选择首页背景；退出登录后同样能看到这张背景。
10. 删除正被用作封面或首页背景的剧照后，对应引用应自动清除。

本地环境使用 Wrangler 模拟 R2，不会占用云端空间。正式环境会让浏览器以 50MB 分片、最多 3 片并发直传 R2。

## 十四、验收旧站数据迁移工具

不连接真实 MySQL 时，先运行内置虚拟快照测试：

```powershell
npm run data:test
```

看到“旧 MySQL 快照转换、D1 导入、外键、文案和 R2 清单验证均通过”即成功。真实迁移时按以下顺序执行，数据库密码只放在当前终端环境变量里，不写入文件：

```powershell
$env:DB_HOST = "旧数据库地址"
$env:DB_PORT = "3306"
$env:DB_USER = "只读用户名"
$env:DB_PASSWORD = "数据库密码"
$env:DB_NAME = "旧数据库名"
npm run data:export -- migration-work/export
npm run data:transform -- migration-work/export/snapshot.json migration-work/converted
npm run data:verify -- migration-work/converted
```

`data:verify` 会把 `import.sql` 导入一次性内存数据库，不会修改本地网站数据库。它会逐表核对 `expected-counts.json` 并执行外键检查；看到“数据量与外键均正确”才进入下一步。

转换结果位于 `migration-work/converted/`：

- `import.sql`：D1 导入文件。
- `verify.sql` 和 `expected-counts.json`：表数量与外键核对。
- `r2-files.json`：旧头像、资料和首页背景的文件迁移清单。
- `warnings.json`：需要人工确认的旧数据问题。

验证通过后还要人工完成两件事：打开 `warnings.json`，确认它是空数组或逐条处理；再检查 `r2-files.json` 的每项 `sources`，保证至少一个旧文件路径真实存在。云端部署恢复后，才把 `import.sql` 导入测试 D1，并用 `data:upload` 上传文件。

`migration-work/` 已被 Git 忽略，不会上传真实数据。先在独立测试 D1/R2 中验收，不能直接覆盖未来正式库。
