# 阶段 0 本地验证记录

日期：2026-09-08

范围：只使用本地 D1 模拟库、固定虚拟密码和测试文字；未连接 Cloudflare 账户、域名、真实数据库、邮件或上传资料。

## 已通过

- Cloudflare Python Worker 能加载 Flask 3.1.3 和 Jinja。
- D1 本地迁移可重复执行；表单写入成功，计数按一次递增。
- Flask 签名 Cookie 和 CSRF 正常：有效令牌写入成功，错误令牌返回 400。
- Flask 能将公开 CSS 转交给 Static Assets，返回 200。
- TypeScript Worker 的 node:crypto 能验证与现有 Werkzeug 相同格式的 scrypt:32768:8:1 测试哈希；本地单次约 54ms。该时间仅是本机结果，不代表云端性能。

## 未通过和已确认限制

- Python Worker 的 hashlib 没有 scrypt，Werkzeug 无法校验现有默认密码哈希。
- Python Worker 的 hashlib 也没有 pbkdf2_hmac；从同步 Flask 路由等待 Web Crypto 会阻塞请求，因此不能采用该临时方案。
- Python Worker 第一次本地加载依赖约 42 秒，热请求恢复正常；这是本地开发冷启动观察值，不能直接推断线上冷启动。

## 待决策

1. 整体业务改为 TypeScript：单 Worker，D1/R2 和密码能力直接，迁移工作量较大。
2. Python Flask + TypeScript 密码服务：可保留模板和较多路由，但多一个 Worker、服务绑定和故障点。
3. 纯 Python并要求所有旧用户重置密码：结构简单，但用户体验差且依赖邮件先完全可用。

建议选择 1。当前项目规模不大，长期维护一个后端比为了保留 Flask 再维护密码服务更清晰；现有 HTML/CSS 设计可以继续复用，不等于把前端全部推倒重做。

## 下一步

用户确认路线后，建立正式的 D1 schema 和首个账号登录切片；云端验证前再创建隔离的测试 D1/R2，并替换 wrangler 配置中的占位 ID。
