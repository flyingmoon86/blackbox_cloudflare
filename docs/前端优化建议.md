# 黑匣子前端优化建议（精修版）

更新：2026-09-12。第一批删除确认、小象压缩、探索提示，以及主题色配置和招新海报基础功能已部署。下文仍是完整目标清单：静态缓存版本机制、头像展示版本、CSS 系统整理及服务端分页等尚未完成，不代表全篇已实现。发布状态与验收限制见《本地验收指南》第二十二节。

依据：核对当前 public/、src/views/、安全中间件、头像服务及上传脚本；保留用户新增的探索提示、主题色和招新海报需求。文件大小与代码问题经过本地检查；网络性能收益是目标，尚未进行本轮线上测速。

## 1. 总体判断与边界

原建议方向基本正确，但需要调整优先级与实施方式：

- 优先修复 CSP 下失效的删除确认，再做小象压缩和首页探索提示。
- 管理员主题色、招新海报是本轮新增产品功能，不能归为单纯 CSS 优化，需要配置保存、权限校验和旧数据回退。
- 不对所有图片直接设置一年缓存，不把所有列表图片一律懒加载，不默认提高上传并发。
- CSS 去重先于主题配置；服务端分页单独推进，不夹带到美术修改中。
- 保留现有分层导航、账号直达图标、作品卡、预览、手机底部导航、审核规则和视频拦截。上一轮这些功能已发布，本轮不重复开发。

PC 保持全站外框固定；列表分页，长表单、指南、预览可内部滚动。手机自然滚动。首页保持两幕，不新增第三幕，不恢复三块大卡片。

## 2. 第一批：可靠性与低成本收益

### 2.1 修复删除确认（优先）

已核对：src/views/resources.ts 的删除表单使用 onsubmit；当前 CSP 不允许内联脚本，因此确认逻辑会被阻止。这是代码层面可确定的缺陷，本轮尚未在正式账号执行删除复现。

改为 data-confirm，由外部 app.js 统一处理 submit。取消时必须 preventDefault；确认后保持现有 POST、CSRF 与管理员校验。不增加 unsafe-inline。

同时检查其他危险操作是否已有统一确认，避免只修一个按钮。验证使用专门测试资料：取消不发请求，确认只提交一次，普通账号仍无法删除。确认框不是权限控制；若要求禁用 JS 时也必须确认，应另加服务端确认页，不能声称 data-confirm 能覆盖这一情形。

### 2.2 压缩默认小象

已核对：默认 JPG 为 2,650,242 字节，约 2.65 MB（2.53 MiB）。建议生成宽 360px 的 WebP，比较质量 75–85，保留小象毛绒细节；目标低于 80 KB，以实际观感和产物为准，不承诺必定 20–40 KB。

使用带内容版本的新文件名，补尺寸或固定比例。先替换有效首页引用、确认无引用再移除旧发布文件；Git 保留原始历史。管理员自选小象也应使用展示图，不能只优化默认图片。

无需引入生产图片处理依赖；实施时确认本地转换工具是否可用，不把“已安装 sharp”当作前提。

### 2.3 让“探索剧团”明显而克制

- 第一幕下方提供清晰的“探索剧团 ↓”，建议文字 16–18px、点击区域至少 44px 高，配一条短细线，保持舞台风格。
- 右侧编号同时显示当前幕名称，例如“01 首页 / 02 剧团”，降低仅靠数字理解的门槛。
- 仅箭头短暂轻微位移，首次出现后停止；减少动画设置下完全静止。
- PC 点击直接切到第二幕；手机点击滚动到介绍，仍支持手指自然滑动。
- 不遮挡左下公告、精选作品、小象或手机底栏；低高度窗口仍可见。键盘可聚焦，焦点样式明确。
- 不用一直闪烁、自动切幕或强制滚轮锁定吸引注意。

## 3. 第二批：管理员主题色

### 3.1 管理入口与操作

在现有“页面管理”增加“外观”分组，提供主题色 HEX 输入框与原生颜色选择器（支持色盘的浏览器使用其系统色盘），两者同步。不引入独立大型取色库。

提供少量预设、当前配色预览、“保存并应用”“取消”“恢复默认”。输入时仅管理员预览变化，保存后才影响访客。错误输入提示并保留上一次有效值。

推荐第一版只开放一个品牌强调色，控制链接、主按钮、选中状态、进度和右上角账号图标；正文、底色与成功/警告/错误色保持语义一致。不要让一个颜色同时替换所有背景与文字。

### 3.2 可读性与实现约束

- 根据强调色生成按钮文字和悬停状态，实际检查文字对比度；过浅颜色可保留为装饰色，但按钮采用可读的派生深色。
- 深色首页与浅色内容页各有派生色，避免同一色值在某一页消失。背景剧照上的文字继续使用稳定暗色遮罩。
- 普通文字目标对比度至少 4.5:1，大字至少 3:1；焦点和控件边界也应清晰，不仅靠颜色表达状态。
- 后端只接受严格的 #RRGGBB，不接收任意 CSS、URL 或 HTML。保存仅限管理员，带 CSRF 校验。
- 可复用现有 page_texts 中独立、带默认值的外观配置；缺字段的旧数据沿用当前主题。更新时合并配置，不能覆盖其他页面文案。
- 当前 CSP 禁止内联样式，不直接输出 style 属性或未授权 style 标签。建议使用同源的主题 CSS 路由，返回经过校验的变量；绑定配置版本，处理更新后缓存。
- 预览也要遵守 CSP，实施时验证外部脚本设置 CSS 属性的实际行为；不为方便而全站放开 unsafe-inline。
- 先整理现有主题变量及覆盖层，再接入可配置色；不继续追加第四套覆盖规则。

验收：深浅主题、导航、账号图标、表单焦点、危险按钮、手机底栏均检查；保存、取消、恢复默认、非法值、旧配置缺失和非管理员写入均验证。

## 4. 第三批：招新海报自然融入第二幕

### 4.1 视觉与响应式

海报放在“加入舞台”区域，与介绍文案组成连续版面，不增加卡片边框，不抢第一幕背景。

- PC 竖版：文案与海报并列，海报约占该区域三分之一，完整显示，限制高度以保留页尾。
- PC 横版：作为招新文案下方的横向展示带，使用 contain，不能裁掉海报里的时间、二维码或报名方式。
- 手机：海报接在招新文案后，宽度适应屏幕、高度随比例变化，自然滚动。点击可打开可缩放预览。
- 没有海报时完全收起区域，不留空框；长介绍、低高度 PC 可以局部滚动，不挤掉联系信息。
- 第一版只展示一张，不做轮播。支持为手机另选一张图；未设置则复用 PC 图片。用 picture/media 等方式选择资源，避免两张图同时下载。

### 4.2 管理与数据

推荐管理员从已审核图片中选择海报，可进入现有上传流程添加新图；不建设另一套文件存储。提供 PC 图、可选手机图、替代文字、清除和桌面/手机预览。

配置引用资料 ID，不复制原文件。保存时校验类型、审核状态与可访问性；图片撤销或删除后安全隐藏。旧配置没有海报时沿用原版面。

首页使用低清展示图，不能为看清二维码自动下载巨大原图。公开海报预览应明确与资料原文件下载权限分开；如需高清公开海报，另生成有尺寸上限的公开展示版本，不放开原文件地址。

海报不得是招新信息的唯一载体：关键时间、对象和联系方式仍写在正文，便于搜索、阅读与辅助技术使用。二维码应在实际手机显示大小下检查可识别性。

## 5. 性能建议的修正

### 5.1 静态缓存：先建立版本机制

现有 max-age=0,must-revalidate 通常会协商缓存，不等于每次完整下载或每次都访问 R2；当前无版本 app.css 也不能据此断言必定返回旧内容。

推荐构建生成内容哈希文件名，覆盖所有 CSS、JS 和随包图片；只有内容不可变的 URL 才设置一年 immutable。旧版本产物保留一个回滚窗口，避免已打开的旧页面引用失效。

若暂不引入构建步骤，统一资源版本只能作为过渡：确保所有引用都更新、部署和回滚同步，采用短缓存。单个手动常量容易漏改，不值得为了“7 天还是 1 天”单独询问用户。

禁止给可替换的 /images/* 一概一年缓存。管理员可修改的背景、头像、主题 CSS 必须有真实内容版本或协商缓存。私有预览、原文件、账号页继续执行原权限与缓存规则，不能统一 public。

Cloudflare _headers 用于静态资源，Worker 动态响应需要代码设置响应头；不要假定它覆盖全部路由。验证浏览器缓存与边缘缓存分别生效，不能仅凭本地响应头推断线上命中率。

参考：[Cloudflare 静态资源响应头](https://developers.cloudflare.com/workers/static-assets/headers/)。

### 5.2 图片加载：区分首屏与后续

首屏主图保持及时加载；当前 theatreHome 已通过 img 输出 /site/hero 并设置 fetchpriority=high，原建议“首页背景只能等 CSS 发现”不适用于这张主图。

先查看实际网络请求，排除全站 body::before 背景与首页主图重复加载；只有确认发现延迟才增加 preload，预加载 URL 必须与实际请求一致。

首屏可见卡片不强制 lazy；后续图片使用 lazy、async 与稳定比例。已有 aspect-ratio 的布局不应未经测量就判定发生 CLS。目标是减少竞争和位移，以浏览器记录验证。

参考：[响应式图片与首屏加载](https://web.dev/learn/design/responsive-images?hl=en)。

### 5.3 头像展示图：兼容旧头像

当前头像链路会存储并返回上传图，缺少独立展示版本。客户端压缩可改善新上传，但不能修复旧头像，也不能替代服务端文件和容量校验。

建议新增小尺寸展示版本并保留原记录；旧头像先回退现有图，再按需或一次性生成展示图。生成、替换、失败清理复用现有存储记账流程，避免孤儿文件或重复计费。客户端压缩前检查解码尺寸，考虑手机大图内存压力。

不默认启用 Cloudflare 图片付费功能；本轮沿用免费约束，工具和额度另核实后才选用。

### 5.4 上传并发：暂不提到 3–4

当前确实串行，但视频仍禁用，其他文件上限有限，尚无瓶颈数据。并发会增加失败重试、在途请求和取消处理复杂度，不一定提升手机网络表现。

本轮保留 1；以后实测比较 1 与 2 的耗时、失败率、请求数，再决定。特别验证取消、断点恢复、进度、失败后其他任务停止和完成幂等。

policy 请求可改为首次选择文件后缓存获取；失败后允许重新获取，避免一个失败 Promise 让整页一直不可上传。真正提交时仍由服务端重新检查配额与权限。

## 6. 维护性：小步整理

- 旧首页 publicHome/memberHome 及专用 helper 当前未发现外部调用，可在再次全项目确认后删除；保留现役 theatreHome。删除范围按引用确定，不能只按旧行号裁切。
- archiveTabs 重复，可抽到小型共享视图片段，保持现有路径和权限。
- CSS 按变量、布局、组件、响应式归并，逐组件比较截图再删覆盖；同时检查旧选择器是否仍供后台页面使用。
- 客户端分页只隐藏 DOM，不减少查询和传输。服务端分页另立任务，保留作品分组、其他资料置后、搜索及稳定提交顺序；检查 SQL LIMIT 是否造成资料无提示缺失。不要保留两套分页同时控制列表。
- 暂不迁移前端框架、不重写整站模板。继续统一转义、共享片段与边界校验即可。

## 7. 执行顺序与验收

1. 修复删除确认；压缩小象；增强探索提示。先完成一批可独立发布的小改动。
2. 梳理主题 CSS，做主题色预览样稿；确认视觉后接入管理员保存。
3. 完成海报的横竖版、PC/手机样稿，再接入配置、展示版本与空状态。
4. 建立静态资源版本机制，处理头像及重复背景请求。
5. 根据真实数据推进服务端分页与上传优化。

每批记录代码完成、本地通过、正式发布三种状态；没有发布不能写“线上已生效”。同步更新本地验收指南；涉及配置/存储时更新架构与迁移文档。代码与文档分开中文提交。

验收包括：

- PC 1366×768、1280×720、低高度窗口；手机 390px 和 360px；放大文字后功能仍可到达。
- 游客、普通账号、队员、管理员的菜单和权限；头像、资料原文件与旧数据不变。
- 横竖海报、无海报、长文案、图片失效；主题极浅/极深色和恢复默认。
- 键盘、触屏、减少动画、弱网、控制台 CSP；首页切幕与导航打开时互不干扰。
- 记录优化前后小象字节数、首页实际图片请求和首屏加载，不能用估算代替测速。
- 代码变更运行 typecheck、format:check；发布前运行 deploy:check，上传或设置改动增加对应回归。仅本文档精修不运行代码测试。
