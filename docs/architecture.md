# 详细架构

> 本文是 README「简明架构」的展开版：请求进来后每一步发生什么、数据之间什么关系、三种常见操作的完整流程。
> 配套阅读：[术语表](glossary.md)、[目录结构](project-structure.md)。

## 一、整体结构

```
                          ┌────────────────────────────┐
  npublackbox.online ───► │                            │
        （主站）           │   Cloudflare Worker        │
                          │   Hono 路由 + 中间件        │
  admin.npublackbox. ───► │   src/index.ts 入口        │
       online（后台）      │                            │
                          └───┬─────────┬─────────┬────┘
                              │         │         │
                              ▼         ▼         ▼
                            D1         R2     Static Assets
                          资料库     文件仓库   public/
                              │         │
                              └────┬────┘
                                   ▼
                          定时触发器（每小时:17）
                          清理过期上传、限流记录、导入明细
```

主站和后台走**同一个 Worker**。后台域名只是在入口处多一道管理员门禁（`src/middleware/admin-portal.ts`），不是另一台服务器。真正的权限判断在每个操作的服务端逻辑里，域名门禁只是第一层。

## 二、一个请求的生命周期

```
浏览器请求
   │
   ▼
① 是静态文件吗？ ──是──► Static Assets 直接返回 public/ 里的内容
   │否                            （不走任何业务逻辑）
   ▼
② 中间件层
   ├── 安全头 / CSP（src/middleware/security.ts）
   ├── 限流检查（src/middleware/request-limits.ts）
   └── 会话还原（src/middleware/session.ts → 读签名 Cookie，查 D1 确认账号有效）
   │
   ▼
③ 后台域名？ ──是──► 管理员门禁（非管理员 302 拦下）
   │否
   ▼
④ Hono 路由分发（src/routes/）
   │
   ▼
⑤ 服务层做业务判断（src/services/）
   ├── 查 D1：这条资料是什么？当前用户能不能操作？
   └── 需要文件时才读 R2
   │
   ▼
⑥ 视图层拼 HTML（src/views/）或返回文件 / JSON
```

关键顺序：**先查资料和权限，再取文件。** 不能反过来——先取了文件再判断权限，等于把文件暴露出去。

## 三、D1 与 R2 的分工

| | D1（数据库） | R2（对象存储） |
| --- | --- | --- |
| 存什么 | 账号、成员、作品、演出版本、演职记录、资源说明、上传任务、审核记录 | 照片、剧本、音频等文件字节 |
| 判断什么 | 「这个文件能不能看、属于谁」 | 什么都不判断 |
| 查询方式 | Worker 直接执行 SQL，无独立数据库服务器 | 按对象键取文件 |
| 备份 | `npm run db:production:backup` 导出 SQL | **目前没有自动备份** |

为什么拆开：说明和权限放 D1、大文件放 R2，查询和下载各做各的事。代价是**两边写入无法合成一次事务**，失败清理要另做处理（见下面上传流程）。

### 数据关系

```
作品（work）
  └── 演出版本（edition）× N        ← 一部剧多次演出，每版独立
        ├── 演职记录（member × 角色/职务）  ← 支持 AB 角、一人多角
        └── 资源（resource）× N     ← 照片/剧本/音频，新上传须选择作品与版本
              └── R2 文件（object key）
```

查询一部剧时，页面按版本分组展示「哪次演出、谁参与、有哪些资料」，不同年份不会混成一条。

数据库结构由 `migrations/` 的编号 SQL 文件管理（当前到 0019）。**本地迁移不会自动作用于生产**，发布时要显式执行。

## 四、三种常见操作的完整流程

### 4.1 访客浏览与下载

```
访客打开作品详情
   │
   ▼
检查作品是否公开 ──隐藏──► 只有管理员能看（其资源也不会因拿到文件地址而开放）
   │公开
   ▼
读取：演出版本 → 演职记录 → 已批准资源
   │
   ▼
展示作品页面

访客点下载
   │
   ▼
资源状态？ ──未批准──► 拒绝
   │已批准
   ▼
所属作品可见？ ──否──► 拒绝
   │是
   ▼
当前用户有下载权限？ ──否──► 要求登录
   │是
   ▼
读 R2，设置文件类型 / 下载方式 / 缓存规则后返回
```

已批准资源的**列表和预览**可以对访客开放；**完整资料页和下载**要求登录。

### 4.2 成员上传资料

```
① 创建任务
   检查：登录？文件大小/类型？版本属于作品？同时进行的上传数？
   通过 → 预留空间（记入 D1 的容量台账）
   任务最长保留 24 小时
   │
   ▼
② 传输文件
   Worker 分片接收（每片最大 50 MiB）→ 写入 R2
   （代码也支持 R2 直传，是否在线上启用需查环境配置，见验证记录）
   传完合并对象
   │
   ▼
③ 建立记录与审核
   合并完成 → 在 D1 建立资源记录 → 判定审核状态
   ├── 管理员投稿 / 低风险规则命中 → 自动批准
   └── 其余 → 等待人工审核
   │
   ▼
   访客可见？──只有「已批准 且 所属作品可见」才可见
```

| 阶段 | 网站做什么 | 访客能否看到 |
| --- | --- | --- |
| 创建任务 | 检查身份和文件规则，预留空间 | 不能 |
| 传输文件 | 分片写入 R2，完成后合并 | 不能 |
| 建立记录与审核 | 写入 D1，确定审核状态 | 获批准且所属作品可见后才能 |

**失败处理**：D1 和 R2 无法一起回滚。网站先处理文件、再写资料记录；中途失败会把文件登记进清理队列，由定时任务重试删除。这能减少「数据库里找不到、桶里还留着」的孤儿文件，但依赖清理任务正常运行。

**容量控制**：网站维护约 9 GB 的软件预算（用已存文件 + 预留空间计算），超过则拒绝新上传。这不是 R2 桶的实际容量上限。

### 4.3 管理员批量导入演职记录

```
管理员上传表格（有列数/行数/文件大小限制）
   │
   ▼
预览匹配结果 ← 先看清楚再决定
   │
   ▼ 确认导入
相关数据库操作作为一个批次执行
   ├── 全部成功 → 导入完成
   └── 任一失败 → 整批回滚（不会只写入一半演职关系）
   │
   ▼
受保护的撤销流程也按批次处理
```

## 五、身份与权限

```
登录成功
   │
   ▼
浏览器保存「签名会话 Cookie」（有效期 14 天）
   │
   ▼
之后每个请求：
   ① 验签（凭据有没有被改动）
   ② 查 D1（账号是否仍然有效、什么角色）
```

密码用 scrypt 保存，保留对历史密码格式的兼容验证。

权限按**操作**判断，不是只分「登录/未登录」：

| 操作 | 访客 | 登录成员 | 管理员 |
| --- | --- | --- | --- |
| 浏览公开内容 | ✓ | ✓ | ✓ |
| 看预览 / 低清图 | ✓ | ✓ | ✓ |
| 下载原件 | — | ✓ | ✓ |
| 上传资料 | — | ✓（通常要审核） | ✓ |
| 审核 / 隐藏作品 / 批量导入 | — | — | ✓ |
| 后台入口 | — | — | ✓ |

写入操作另有两道防线：**同源检查 + CSRF 令牌**，防止其他网站借用已登录浏览器发起修改。页面限制嵌入和脚本来源，敏感响应不让浏览器随意缓存。生产环境的 Turnstile 人机验证只用于注册、匿名反馈等指定流程。部分频繁请求有限流。

## 六、缓存与静态资源

- 静态文件（`public/`）由 Static Assets 直接返回，不走业务逻辑。内容哈希的文件可长缓存。
- 图片在边缘可能短期缓存以减少重复读取，但**每次访问仍先经过资料和权限检查**，缓存不绕过权限。
- 私有文件每次先授权再处理 HEAD/Range/304 请求。

## 七、定时维护

每小时第 17 分钟运行，负责：

- 清理过期上传任务（超过 24 小时）
- 重试删除清理队列里的失败文件
- 清理过期限流记录和导入明细

它能清理过期记录，**不能代替备份和人工检查**。

## 八、技术栈速查

| 组件 | 是什么 | 对应代码 |
| --- | --- | --- |
| Cloudflare Worker | 服务器程序，处理全部动态请求 | `src/index.ts` |
| Hono | 路由框架，把网址交给对应处理 | `src/routes/` |
| D1 | 数据库（SQL） | `migrations/` + 各 service 查询 |
| R2 | 对象存储（文件） | `src/storage/` |
| Static Assets | 静态文件直出 | `public/` |
| Wrangler | Cloudflare 命令行工具 | `scripts/wrangler.mjs` |

想改某个具体页面或规则但不知道代码在哪，查 [目录结构](project-structure.md) 的快速定位表。
