# 数据库连接管理评估

评估日期：2026-09-22。依据当前工作区源码、Wrangler 配置、Cloudflare 官方文档和本轮本地回归；工作区包含尚未提交的其他改动，不等同于当前线上版本。

## 结论

保持原生 D1 绑定，不引入传统连接池，不接入 Hyperdrive，不迁移数据库。未发现应用自行建立数据库连接、遗漏释放连接或需要靠连接池修复的证据。线上是否存在排队、过载和慢查询尚未测量，不能将其解释为已经排除。

## 实际架构与连接归属

- `wrangler.jsonc`：TypeScript/Hono 单 Worker，主站和管理域名共用生产 Worker、一个生产 D1 绑定 `DB`，文件存储使用 R2，静态资源由 Static Assets 提供。生产配置已有 Smart Placement 和 observability；本轮未读取控制面确认实际生效状态。
- `src/types.ts`：`DB: D1Database`。`package.json` 无 pg/mysql2 等传统 SQL 驱动、ORM 或池依赖。Node.js 主要用于本地工具链；`nodejs_compat` 不会把 Worker 变成长驻 Node 数据库服务器。
- 源码直接使用 `env.DB.prepare().bind().first()/all()/run()`，多语句使用 `batch()`。prepare 创建语句对象，不是在每次请求里进行 TCP/TLS/数据库认证。应用没有需要成对调用的 connect/release/close，也没有应由 finally 归还的数据库连接。
- D1 是托管的 SQLite SQL 数据库。连接访问由平台绑定抽象管理；这里不应把实现描述为“项目已经配置了一个传统连接池”。[D1 API](https://developers.cloudflare.com/d1/worker-api/d1-database/)
- Cloudflare 明确说明 Hyperdrive 不支持 D1，D1 无需传统数据库建连往返。Hyperdrive 面向通过 TCP 驱动访问的 PostgreSQL/MySQL 等数据库。[Hyperdrive FAQ](https://developers.cloudflare.com/hyperdrive/reference/faq/)

## 源码检查结论

### 连接、并发与等待

未发现重复建连或连接泄漏。首页第一组有 4 个并行任务，后台通知有 2 个并行数据库调用；没有发现这些入口无界创建连接。登录请求会按当前用户 ID 再查角色和状态，这是权限即时生效所需的读取，不宜简单缓存掉。

D1 单实例按顺序执行查询；过量请求可能排队，队列满时过载。每次 Worker 调用最多同时打开 6 个 D1 连接这一平台限制，不是站点总用户上限，也不是应该配置 pool.max=6 的理由。Promise.all 可以减少应用串行等待，但不会让单个 D1 实例同时执行多条 SQL。[D1 FAQ](https://developers.cloudflare.com/d1/reference/faq/)

未获取生产流量、D1 执行统计或过载错误分布，不能确认存在并发过量、队列拥塞，也不能给出可承载 QPS。

### 封装、事务与恢复

- 目前封装按业务服务拆分，直接传入 D1Database，适合当前规模；无需为了连接管理再包一层 ORM。
- `src/services/credit-import/store.ts` 的 atomic 使用 batch；提交/撤销将 revision、guard 校验与写入放入同一批次。约束冲突映射为 409，未知异常继续抛出。
- `src/services/uploads.ts` 使用条件更新、租约和 source_upload_task_id 防重复完成，元数据和台账用 batch 提交。业务租约与数据库连接是两回事。
- `src/services/file-cleanup.ts` 先记录删除意图，再操作 R2；失败保留重试任务。D1 与 R2 不存在共同数据库事务，此恢复模式合理，连接池不能提供跨服务原子性。
- D1 batch 顺序执行，任一语句失败回滚整批；多个独立 await 不自动构成事务，未来新增多表不变量仍应在 batch、约束或触发器内保证。Sessions API 提供顺序一致性，不是交互事务或连接池。[batch 与 Sessions API](https://developers.cloudflare.com/d1/worker-api/d1-database/)

这是关键链路抽查和回归结论，不是所有业务路由不存在竞争条件的证明。

### 已确认的诊断不足与访问开销

1. `src/middleware/errors.ts` 只记录 requestId、路由、状态和总耗时；Server-Timing 也是 Worker 总处理时间，缺少 SQL 耗时、读取行数和数据库错误分类。现有应用日志不能独立证明慢请求来自 D1。
2. `src/routes/productions.ts` 作品详情在权限检查后依次读取演职员、版本、资料总数、资料列表及按身份选择的数据，存在多次串行往返；实际延迟占比待测。可在测量后合并或有限并行独立读取，保留依赖版本选择和分页总数的顺序。
3. `src/routes/admin.ts` 通知每次读取当前管理员全部历史 notification_key；随历史增长返回集合会扩大。客户端当前每 60 秒轮询且隐藏时停轮询。若测量确认开销显著，可只查询本次候选通知键，或改为游标；不要直接加索引或连接池假定解决。

已有站点设置 30 秒缓存、资料分页、50 行导入上限、清理任务批量上限和上传任务限制，应保留。未确认上述开销已成为生产瓶颈，因此本轮不改业务实现。

## 最小后续验证方案

1. 先用现有 D1 Metrics/Query Insights 检查代表时段的查询次数、SQL 延迟、读取/写入行数及错误，与 Worker 请求量和墙钟耗时对应。首页、作品详情、通知、导入分开看；记录版本、冷热缓存、身份、时段与样本数。[D1 指标](https://developers.cloudflare.com/d1/observability/metrics-analytics/)
2. 如平台数据不足，再在热点业务调用增加采样观测：固定查询标签、调用墙钟耗时、D1 meta 的 duration/rows_read/rows_written、成功状态和白名单错误类别；不记录 SQL 参数、用户资料或原始异常。将 SQL 执行与调用耗时区分，但不能直接把二者差值全部视为排队。[D1 返回元数据](https://developers.cloudflare.com/d1/worker-api/return-object/)
3. 对高读取量查询使用合成数据和 EXPLAIN QUERY PLAN 判断索引；在独立本地/预发布环境逐步提高并发，比较 p50/p95、吞吐、错误率与查询数。生产压测与配置变化另行确认，不能把本地 SQLite 耗时当作 Cloudflare 网络性能。
4. 保持现有有限并发和批次。若确认过载，先降低热路径查询量、限制重型任务并发；单个 isolate 内的全局 semaphore 不是全站限流。
5. D1 官方查询时限为 30 秒，整个 batch 也受此限约束。当前无需增加池等待超时。Promise.race 超时只会停止等待，不能当成取消 D1 写入；写入结果不明时应查询业务状态，不能盲目重放。[D1 限制](https://developers.cloudflare.com/d1/platform/limits/)

现有代码未使用 withSession，不能假定享有读副本收益。将来只有测量证实主实例读取压力或距离问题时才评估 read replication，并单独保证登录、权限、隐藏状态和写后读取的一致性；本轮不调整生产配置。

## 成本与实施决定

传统池不能减少当前不存在的握手成本，也不能提高单实例 SQL 执行吞吐。人为增加池封装会带来队列、超时、重试、isolate 生命周期和测试维护负担。

若未来改为外部 PostgreSQL/MySQL，再评估 Hyperdrive 与对应驱动，届时涉及数据库费用、服务配额、凭证/TLS、迁移、SQL/触发器兼容和备份运维；这不是当前 D1 的最小优化方案。不假定 Hyperdrive 一定收费，也不在没有套餐和流量数据时估价。

本轮仅归档评估，不增加依赖、不修改业务代码、迁移或生产配置、不部署、不推送。
