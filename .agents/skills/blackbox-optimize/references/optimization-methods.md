# 黑匣子优化方法

按当前任务只读对应方法。每种方法都先遵守上级 `SKILL.md` 的产品、权限、数据兼容和发布边界。

## `audit_context(scope)`：确认真实现状

适用：接手项目、继续优化、判断某功能是否完成。

输入：页面、流程或模块范围。输出：已实现、已验证、已发布、待确认四类事实。

1. 读 README、本地验收指南、验证记录和最近提交；历史草案只作背景。
2. 用 `rg` 找实际路由、视图、服务、迁移和测试，检查 git 状态。
3. 文档与代码冲突时以代码和可重复测试为准；生产状态只采用明确的发布记录或实时只读核对。
4. 不读取私密备份、旧密码或 Secret 值。

## `review_change(target)`：审查改动而非泛审项目

适用：工作区、分支、提交或 PR 的优化审查。默认只读。

1. 解析 base/head、提交数、未提交文件；排除锁文件、生成物、快照、字体和二进制。
2. 读完整 diff，包括删除行；从改动文件扩到直接调用者/消费者，主题 token 最多再扩一层。
3. 将问题标为 `Introduced`、`Regression` 或 `Pre-existing`。只让前两类影响本次结论，预存问题最多列三个。
4. 界面改动按 accessibility → layout → writing → typography → colors → UI 顺序检查；正确性、安全、性能另列，不混成审美意见。
5. 每项给出文件行号、当前证据、用户影响和最小修复。无实际改动时停止并说明可选审查目标，不擅自审最后一次提交。

## `improve_interface(scope)`：实施界面优化

适用：页面布局、文案、颜色、字体、动效和交互。

1. 先识别页面用途、主要任务、支持宽度、既有 token、CSS 分层和真实内容长度。
2. 修复优先级：删除多余层 → 使用原生元素 → 复用现有组件/token → 修正值 → 最后才新增抽象。
3. 可访问性底线：原生语义、可见焦点、键盘等价路径、明确标签、错误恢复、非颜色单一提示、减少动画、200% 缩放和 320px 不丢功能。
4. 布局以空间和共享边缘建立层级；断点由内容崩坏点决定；媒体可铺开，文字和控件留安全边距；隐藏内容必须有提示。
5. 文案沿用站内术语；按钮动词开头；错误说明下一步；空状态提供出口；破坏性操作使用严肃、明确文案。
6. 字体控制数量和层级，正文保持可读行长；输入在手机不小于 16px；截断内容必须可展开；动态数字用等宽数字。
7. 颜色只使用严格 HEX 主题体系；测量实际渲染前景/背景，不估算对比度；状态不能只靠颜色；危险/成功色不借作装饰。
8. 动效只动画必要属性，频繁操作不超过 150ms；支持 `prefers-reduced-motion`；动画后仍保留静态状态线索。
9. 在现有 Hono 服务端页面、CSS 和原生 JS 中实现，不为界面优化引入框架或动效依赖。

## `stress_state(component_or_flow)`：压测真实状态

适用：怀疑组件只适配了理想数据，或表单/卡片在边界状态下不稳。

从真实输入能力选择场景，不机械组合全部轴：

- 数据：空、单条、分页边界、上限数量、重复、已失效引用。
- 文本：空、正常、很长、不可断字符串、旧年份、中文标点。
- 状态：默认、悬停、焦点、处理中、成功、失败、禁用、待审、撤销。
- 身份：游客、普通账号、认证队员、管理员、禁用账号、强制改密。
- 环境：1366×768、低高度、390px、360/320px、200% 缩放、键盘、触屏、减少动画、无 JS 回退。

优先用现有路由和合成数据构造；不碰生产数据。只把实际观察到的破坏写成问题，预测项写“未验证”。修复后重跑失败场景和邻近正常场景。

## `compare_variants(piece, axis)`：比较设计方案

仅在用户要求方案比较、或产品结果确有未决选择时使用。

1. 一次只选一个界面单元和一个主轴：结构、密度、强调、字体或文案。
2. 默认三个真正不同的方向，不做三个换色版本；都必须先满足可访问性底线。
3. 放进真实页面和真实邻接内容，用 URL 参数或仅开发环境开关切换；测试数据必须合成。
4. 展示各方案适用情景与代价，不替用户暗选。选定后删除未选方案和临时开关。

## `explain_effect(target)`：解释现有界面效果

适用：分析某个渐变、层次、动效或外部参考站点如何实现。

1. 只回答指定效果；按绘制顺序查元素、伪元素、背景、滤镜、遮罩和上层覆盖。
2. 每个结论标为：实测（页面/计算样式/像素）、推导（由实测计算）、推测（意图判断）。
3. 截图只能重建可能方案，不能宣称读到源码、token、断点或动画。
4. 最后提炼可迁移机制，不复制外站品牌资产、字体或整段编译代码。

## `optimize_performance(flow)`：先测量再优化

适用：页面慢、R2/D1 成本、缓存、上传或交互延迟。

1. 先定义指标和基线：TTFB、Worker 总处理、D1 查询数、R2 读取、传输字节、缓存命中、主线程长任务或交互延迟。
2. 分清静态资源、公共动态图片、私有文件和 HTML；只有跨用户完全相同且每次先完成权限/引用校验的字节可以共享缓存。
3. 优先删重复查询、并行独立查询、减小传输和复用现有预览；索引必须由实际查询与查询计划支持。
4. 不把 `Server-Timing` 当 CPU/D1 时间，不把一次本地 dry-run 当线上网络收益，不凭猜测增加上传并发。
5. 记录测试网络、时段、样本数、缓存冷热和部署版本；优化后用同方法复测，并保留正确性回归。

## `harden_write_flow(flow)`：加固权限与数据写入

适用：注册、登录、审核、上传、移动、删除、页面设置和账号管理。

1. 列出正常身份、越权身份、失效会话、跨站请求、重复请求、并发请求和中途失败。
2. 服务端依次验证身份/状态、角色、CSRF/同源、输入范围、对象存在性和父子归属；前端隐藏不算权限。
3. 多表业务尽量由同一 D1 transaction/batch/触发器原子完成；审核记录处理人、理由、时间和规则来源。
4. 文件操作先在 D1 记录意图，再处理 R2；失败进入可重试清理；共享对象和未完成上传不能误删。
5. 对网络结果不确定的写操作不自动重试；先刷新核对。幂等端点验证重复完成只产生一次业务记录。
6. 测试使用合成数据，覆盖成功、400/401/403/409/413/429/500 和恢复路径中实际相关的状态。

## `verify_browser(scope)`：浏览器实测

适用：任何视觉、键盘、触屏、网络或运行时结论。具体工具选择见 `tool-routing.md`。

1. 先启动本地环境并确认目标 URL/身份，避免误写生产。
2. 至少检查 1366×768 与 390px；拥挤页面加低高度、360/320px和 200% 缩放。
3. 执行主要任务及失败路径；检查 Tab 顺序、焦点、Esc、触屏、减少动画和无 JS 回退。
4. 检查控制台、网络状态/缓存头、可访问名称与页面截图；运行时才可判断的内容不得只看源码。
5. 记录页面、身份、数据、视口、实际结果和未覆盖项；截图不得含密码、邮箱、私有资料或令牌。

## `release_ready(scope)`：交付与发布前收口

1. 运行与改动相关的测试、类型和格式；发布前运行 `npm run deploy:check`。
2. 确认 git diff 只含本任务内容，迁移为新增且未改历史文件；核对是否有待执行迁移。
3. 分别说明：源码完成、本地自动检查、浏览器验收、线上状态。更新本地验收指南和验证记录。
4. 没有用户本轮明确部署授权时停止；Git 提交或推送不等于上线。
5. 获得授权后按指南备份、增量迁移、部署和线上冒烟；禁止本地整库覆盖生产。
